## Project Overview

This repo is a master's thesis project investigating when Kubernetes becomes worth the overhead compared to a single-VM workflow executor (Dagster). It contains:

- **LaTeX thesis** (`docs/`)
- **Experiment scripts** (`scripts/`)
- **Workload source code** (`src/workload/`)
- **Data directory** (`data/`) — structured but not yet populated
- **Notebooks** (`notebooks/`) — interactive analysis and setup guides

## Development Setup

### Prerequisites

| Tool | Version | Purpose |
|------|---------|---------|
| Python | 3.12+ | Scripts and analysis |
| jq | any | Label sync script |
| gh | any | GitHub CLI (issue/label sync) |
| latexmk | any | Build the PDF |

### Install Python dependencies

```bash
pip install psutil psycopg2-binary pandas matplotlib numpy scipy
```

### Clone and verify

```bash
git clone https://github.com/sirajwahaj/thesis.git
cd thesis

# Verify the dry-run works
make dry-run
```

## Branching Strategy

| Branch pattern | Purpose |
|---------------|---------|
| `main` | Stable, always compiles |
| `feat/THESIS-XXX-short-description` | New feature or ticket work |
| `fix/short-description` | Bug fixes |
| `docs/short-description` | Documentation-only changes |
| `data/exp1-results` | Committing experiment data |

**Always branch off `main`.** Never commit directly to `main`.

```bash
git checkout main
git pull
git checkout -b feat/THESIS-003-workload-dockerfile
```

## Commit Messages

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short description>

[optional body]
```

| Type | When to use |
|------|------------|
| `feat` | New script, notebook, or feature |
| `fix` | Bug fix |
| `docs` | README, CLAUDE.md, LaTeX changes |
| `data` | Adding experiment result files |
| `chore` | Makefile, CI, dependency updates |
| `refactor` | Code restructuring without behaviour change |

**Examples:**

```
feat(scripts): add collect_pod_timing.py with scheduling latency
fix(runner): handle missing metadata.json gracefully
docs(latex): fill in exp1 VM degradation table with results
data(exp1): add L1–L3 run data from VM experiment
```

## Pull Request Process

1. **Open an issue first** for non-trivial changes (use the templates).
2. **Create a branch** following the naming convention above.
3. **Make your changes** — keep PRs focused and small.
4. **Test locally:**
   ```bash
   make dry-run          # verify runner works
   python scripts/analyze_results.py  # verify analysis script
   make pdf              # verify LaTeX compiles (if you changed .tex files)
   ```
5. **Open a PR** — the PR template will guide you.
6. **Wait for review.** Address any comments.

## Code Conventions

### Python

- Follow **PEP 8**
- Use **type hints** where practical
- Include a module-level docstring explaining purpose and CLI usage
- Use `argparse` for CLI arguments — no hardcoded paths
- Scripts must handle `SIGTERM`/`SIGINT` gracefully (collector scripts)
- Do not commit credentials or personal paths

### Shell scripts

- Start with `set -euo pipefail`
- Use `--long-flag` style arguments
- Include usage instructions at the top as a comment block
- Test with `bash -n script.sh` before committing

### LaTeX

- One `.tex` file per section — never edit `chapter.tex` hub files directly
- Leave `% TODO:` comments where data still needs to be filled in
- Use `\label{sec:...}` on every `\section`
- Figures go in `docs/figures/` (generated by `make copy-figures`)

### Data files

- **Never commit raw experiment data** (CSV files from runs) unless specifically discussed
- `.gitkeep` files maintain the directory structure
- `metadata.json` is always committed alongside any data
